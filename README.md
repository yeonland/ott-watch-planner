## 1. 제품 한 줄 소개

내 취향에 맞는 작품은 쉽게 찾고, 본 기록은 재미있게 남기고, 구독은 볼 때만.

여러 OTT를 이용하면서 무엇을 볼지 고민하고 구독료를 낭비하는 느낌이 드는 사람에게, 현재 구독 상태·보고 싶은 작품·결제일을 연결해 다음 행동을 제안하는 콘텐츠·구독 의사결정 도구다.

### 핵심 가치 제안

1. **선택 피로 감소:** 오늘 볼 작품을 몇 개의 적합한 후보로 좁힌다.
2. **구독 결정 지원:** 보고 싶은 작품과 결제일을 함께 보여 주어 유지·중단 시점을 검토하게 한다.
3. **기록 부담 최소화:** 전체 시청 이력을 매번 입력하지 않아도 시작할 수 있게 한다.

이 서비스가 보장해야 하는 것은 '최고의 AI 추천'이 아니라 사용자가 적은 정보를 제공해도 더 빠르고 편하게 결정할 수 있는 경험이다.

## 2. 플랫폼 선택: 웹앱부터 시작

### 결론

1차는 모바일 우선 반응형 웹앱으로 만들고, 핵심 기능이 검증되면 PWA 설치 기능을 추가한다. Flutter 기반 iOS·Android 앱은 반복 사용과 네이티브 기능의 필요성이 확인된 뒤 재검토한다.

### 왜 지금 Flutter가 아닌가?

- 초기에는 앱스토어 입점보다 사용자 테스트 링크를 공유하고 빠르게 수정하는 일이 중요하다.
- 현재 기획의 핵심 기능은 구독 정보 입력, 작품 탐색·찜, 결제일 확인 등으로, 네이티브 기능이 없어도 검증할 수 있다.
- 제작자의 현재 강점은 HTML·CSS·JavaScript 기반 UI 구현 경험이다. 익숙한 기술을 활용하면 기획·사용성 검증에 더 많은 시간을 배정할 수 있다.
- 웹앱은 URL로 공유하기 쉽고, 지원 브라우저에서는 PWA로 홈 화면에 설치할 수 있다. 다만 설치·알림·백그라운드 동작은 운영체제 및 브라우저에 따라 다르다.
- Flutter는 동일 코드베이스로 모바일과 웹을 함께 개발하기에 유리하지만, Dart 및 Flutter 학습과 웹 배포·접근성·검색 최적화 관련 고려가 추가된다. Flutter 공식 문서도 웹에서 앱 중심의 상호작용 경험에 적합하다고 설명하며, 글 중심의 정적 콘텐츠 사이트에는 일반 웹 기술이 더 적합할 수 있다고 안내한다.

### 플랫폼 비교

| 기준 | 반응형 웹앱 / PWA | Flutter 앱 |
|---|---|---|
| 첫 사용자 테스트 | 링크 공유로 빠름 | 앱 배포 시 설치 장벽이 생길 수 있음 |
| 현재 기술 경험 활용 | 높음 | 별도 학습 필요 |
| 모바일 UX | 충분히 구현 가능, 브라우저 차이 고려 | 네이티브 앱 경험에 유리 |
| 홈 화면 설치 | 지원 브라우저에서 가능 | 앱스토어 또는 직접 배포 경로 활용 |
| 검색·공유용 콘텐츠 페이지 | 일반 웹 기술이 유리 | Flutter 웹은 앱 중심 화면에 더 적합 |
| 추후 iOS·Android 공통 코드 | 별도 앱을 만들면 UI 일부 재구현 가능 | 공통 코드 재사용에 유리 |
| 지금의 추천 | **1순위** | 검증 뒤 검토 |

### 개발 방식 제안

- **클릭 가능한 디자인 검증:** Figma 또는 HTML 프로토타입
- **첫 사용자 테스트용 웹앱:** React + TypeScript + Vite를 기본 후보로 한다. 제작자가 React 사용에 익숙하지 않다면 먼저 정적 HTML·CSS·JavaScript로 흐름을 검증해도 된다.
- **개인 기기에서만 테스트:** 임시로 localStorage를 활용할 수 있다.
- **외부 사용자 데이터를 받는 베타:** 사용자별 데이터 분리를 갖춘 백엔드/DB를 사용한다. 예: Supabase 또는 Firebase. 인증·접근 권한 규칙을 설정하고, API 비밀 키를 프런트엔드에 노출하지 않는다.
- **PWA:** 핵심 흐름이 안정화된 다음 manifest, 앱 아이콘, HTTPS, 오프라인/캐싱 필요성 등을 검토한다.

처음부터 React, 인증, 데이터베이스, PWA, Chrome 확장, AI를 모두 한 번에 만들지 않는다.

## 3. 타깃 사용자 가설

### 메인 타깃

OTT를 2개 이상 구독하고, 볼 콘텐츠를 고르는 데 시간을 쓰지만 시청 기록을 꼼꼼히 입력하는 것은 귀찮아하는 사람.

대표 특성:

- 넷플릭스·티빙·웨이브 등 2개 이상의 OTT를 번갈아 이용한다.
- 앱을 열어도 무엇을 볼지 몰라 여러 서비스를 오가거나 결국 시청을 포기한다.
- 구독료를 낭비하는 것 같아도 이용량을 정리해 보지 않는다.
- 전체 시청 기록 작성보다는 '보고 싶은 작품 찜하기'나 '결제일 확인' 정도는 할 의향이 있다.

### 서브 타깃

1. **특정 작품 공개 시기에만 몰아보는 사용자:** 공개 일정에 맞춰 구독을 켜고 끄고 싶어 한다.
2. **관심 작품이 많고 잊어버리는 사용자:** 보고 싶은 작품을 저장하고 어디에서 볼 수 있는지 확인하고 싶어 한다.
3. **가계 지출을 관리하는 사용자:** 여러 디지털 구독 서비스를 한 번에 살펴보고 싶어 한다.

### 초기에는 타깃으로 삼지 않을 사용자

- 한 OTT만 이용하고 콘텐츠 선택에 어려움이 없는 사람
- 상세 통계와 모든 시청 이력을 적극적으로 기록하는 헤비 트래커(향후 고급 기능 타깃이 될 수 있음)
- 시작부터 TV·모바일 앱까지 모든 기기의 완전 자동 시청 기록 수집을 요구하는 사용자

### 페르소나 예시 — 검증 전 가상 페르소나

**이름: 민지(가상 인물), 27세**

- OTT 3개를 구독하지만 매번 볼 작품을 고르느라 시간을 쓴다.
- 신작을 보고 싶어서 구독을 유지하지만, 다음 달에도 볼 콘텐츠가 있는지는 따로 확인하지 않는다.
- 작품을 볼 때마다 앱에 기록을 입력하고 싶지 않다.
- 보고 싶은 작품을 찜해두고, 결제일에 '이번 달은 유지할까?'라고 한 번에 확인하고 싶다.

**검증할 질문:** 이런 불편이 사용자에게 충분히 자주 발생하는가? 현재 키노라이츠·JustWatch 등 기존 서비스를 사용하지 않는 이유가 있는가? 어떤 결과라면 실제 구독 결정을 바꿀 것인가?

## 4. 문제 정의와 포지셔닝

### 문제 정의

OTT 사용자는 서로 다른 앱에서 작품을 탐색하고, 볼 작품을 고르고, 구독료와 결제일을 관리해야 한다. 여러 정보를 따로 확인하는 데 드는 수고 때문에 무엇을 볼지 결정하지 못하거나, 이용하지 않는 구독을 계속 유지할 수 있다.

### 포지셔닝 가설

콘텐츠를 검색하는 데서 끝나지 않고, '지금 볼 작품'과 '구독을 유지할 시점'을 연결해 주는 도구.

### 경쟁 우위를 단정하지 않기

키노라이츠는 통합 검색·제공처 정보·가격 비교·콘텐츠 추천·취향 분석 등과 겹치는 기능을 제공한다. JustWatch 역시 제공처 필터, 개인화 추천, 통합 Watchlist를 제공한다. Trakt는 시청 이력과 Watchlist, API 등을 제공하며 지원 서비스의 자동 동기화도 일부 제공한다.

따라서 'OTT 통합 검색', '찜 목록', '개인화 추천'을 자체로 독점 기능이라고 주장하지 않는다. 차별점은 다음 가설을 검증하는 데 있다.

- 많은 정보를 입력하지 않아도 핵심 가치를 경험할 수 있다.
- 추천 목록에 현재 구독 중인 서비스와 실제 결제 상태를 반영한다.
- 작품의 공개 시기와 결제일을 연결해 유지·중단을 검토하기 쉽게 한다.
- 사용자가 매번 기록을 작성하지 않고도 다음 행동을 결정할 수 있다.

## 5. 핵심 사용자 시나리오

### 시나리오 A — 오늘 뭐 볼까?

1. 사용자가 홈 화면을 연다.
2. 현재 구독 중인 OTT와 선호 장르를 바탕으로 작품 3~5개를 확인한다.
3. 각 카드에서 추천 이유와 확인된 시청 제공처를 본다.
4. 찜하기, 봤어요, 관심 없음 중 하나를 선택한다.
5. 다음 추천과 보관함에 변경 사항이 반영된다.

**성공 기준:** 사용자가 여러 OTT를 돌아다니지 않고 작품 후보를 좁힌다.

### 시나리오 B — 다음 달에도 결제할까?

1. 사용자가 구독 관리 화면을 연다.
2. OTT별 실제 결제액과 다음 결제일을 확인한다.
3. 보고 싶은 작품, 확인된 공개 일정과 대조한다.
4. 서비스별 유지, 해지 검토, 나중에 다시 구독 상태를 선택한다.
5. 결제일 전에 웹앱에서 확인하거나 자신의 캘린더에 알림을 등록한다.

**성공 기준:** 사용자가 구독 유지 여부를 의식적으로 검토한다. 앱은 사용자 허가 없이 구독을 해지하거나 결제하지 않는다.

### 시나리오 C — 나중에 볼 작품을 잊지 않기

1. 사용자가 작품을 검색하거나 작품 카드를 누른다.
2. 작품을 보관함에 추가한다.
3. 나중에 보관함에서 제공처와 확인 가능한 공개 정보를 살펴본다.
4. 작품을 본 뒤 봤어요로 표시하거나 관심 없음으로 제외한다.

**성공 기준:** 저장한 작품이 사라지지 않고, 검색이나 외부 OTT 이동을 도와준다.

## 6. MVP 화면 구성 — 5개 핵심 화면 + 월간 통계 확장 화면

### 화면 1. 시작 설정 / 내 구독

- OTT 선택
- 실제 결제액과 결제 주기 입력(월간·연간 등)
- 다음 결제일 입력
- 선호 장르 선택(선택 사항)
- 나중에 설정할 수 있는 건너뛰기 제공
- 민감한 OTT 비밀번호 또는 계정 로그인 정보는 수집하지 않음

**필수 동작:** 저장·수정·삭제가 가능하고, 이후 화면의 총액과 결제일에 반영된다.

### 화면 2. 홈 — 오늘 뭐 보지?

- '지금 볼 작품' 3~5개
- 추천 이유(예: 선호 장르, 저장한 유사 작품)
- 현재 구독 중인 곳에서 볼 수 있는지 표시(정보가 검증됐을 때만)
- 찜하기 / 봤어요 / 관심 없음
- 다음 결제 예정일 또는 구독 검토 항목

**필수 동작:** 추천 카드와 버튼이 실제 상태 변경과 연결된다. 초기는 규칙 기반 추천으로 충분하다.

### 화면 3. 작품 보관함

- 보고 싶은 작품 / 본 작품 / 관심 없음 필터
- 작품 삭제·상태 변경
- 제공처 정보가 확인된 경우 표시
- 검색

**필수 동작:** 같은 작품의 상태가 홈과 상세 화면에 동기화된다.

### 화면 4. 구독 관리

- OTT별 구독 상태, 실제 결제액, 주기, 다음 결제일
- 월 환산액과 총합(월간·연간 결제 구분)
- 유지 / 해지 검토 / 나중에 재구독 상태
- 결제일 직접 수정
- 캘린더 등록 또는 복사 기능은 간단한 형태로 시작

**필수 동작:** 합계 계산과 날짜 표시가 정확하다. 실제 취소는 사용자에게 공식 OTT 관리 페이지에서 수행하도록 안내한다.

### 화면 5. 작품 상세

- 제목, 장르, 줄거리(데이터 출처와 이용 조건 확인)
- 추천 이유
- 확인된 제공처와 공식 시청 페이지 링크
- 찜하기 / 봤어요 / 관심 없음

**필수 동작:** 모든 화면이 동일한 작품 데이터를 사용한다.

### 확장 화면 6. 월간 통계 — '이번 달 나는 뭘 다봄?'

**우선순위: P1.** 통계는 기록을 남기는 재미와 재방문 이유를 제공할 수 있지만, 핵심 기록 기능이 먼저 작동해야 신뢰할 수 있는 결과를 낼 수 있다. 통계를 위해 사용자가 매번 많은 정보를 입력하도록 만들지 않는다.

#### MVP 통계 항목

- **이번 달 기록한 작품 수:** 해당 월에 봤어요로 완료 처리한 고유 작품 수. 같은 작품을 여러 번 열어도 중복 집계하지 않는다.
- **이번 달 많이 기록한 장르:** 이번 달 완료 처리한 작품의 대표 장르를 기준으로 집계한다. 초기에는 작품당 대표 장르 1개를 정해 중복 계산을 줄인다.
- **이번 달 가장 많이 기록한 OTT:** 해당 OTT에서 완료한 작품 또는 에피소드 기록 수를 기준으로 표시한다. 실제 시청 시간 데이터가 없으면 이를 시청 시간이나 실제 재생량으로 표현하지 않는다. 필요하면 라벨을 '가장 많이 기록한 OTT'로 명확히 한다.
- **최근 다봄 기록:** 완료한 작품의 제목, 기록 날짜, 선택적 평점.
- **선택 지표:** 평점을 입력한 경우 평균 평점 또는 이번 달 가장 높은 평점 작품을 표시한다.

#### 통계 계산 원칙

- 현재 데이터로 계산할 수 있는 값만 표시한다. 시청 시간을 직접 기록하거나 신뢰할 수 있는 데이터로 확보하지 못했다면 '총 시청 시간'을 추정해서 표시하지 않는다.
- 영화·드라마의 작품 유형, 회차 진척도, 완료 여부를 구분한다. 시리즈의 에피소드 수를 입력한 경우 '완료한 작품 수'와 '완료한 에피소드 수'를 별도로 표시한다.
- 통계 기간은 달력 기준 월간으로 계산하고, 사용자 로컬 날짜 기준을 사용한다.
- 기록이 부족할 때는 0 또는 임의의 샘플 통계를 진짜 이용 기록처럼 보여주지 않는다. 빈 화면에는 '작품을 기록하면 이번 달 취향 리포트가 만들어져요'와 기록 추가 CTA를 보여준다.
- 테스트용 가상 데이터를 보여주는 개발 모드에서는 '예시 데이터'임을 명확히 표시한다.

#### 월간 공유 카드 — 통계를 이미지로 저장하기

**목적:** 시청 기록을 단순한 데이터가 아니라 공유하고 싶은 개인화된 결과로 바꿔 기록 습관과 자연스러운 입소문을 유도한다. 다만 공유 카드 자체가 사업성을 증명하는 것은 아니므로 저장·공유율과 기록 기능 사용률을 함께 검증한다.

**카드 기본 구성**

- 브랜드: 다봄 Dabom
- 기간: 예) 2026년 10월
- 숫자: 이번 달 완료 작품 수
- 취향: 가장 많이 기록한 대표 장르
- OTT: 가장 많이 기록한 OTT 또는 '가장 많이 기록한 곳'
- 짧은 카피 예시: 이번 달은 로맨스를 다봄 🌷
- 하단에 작은 로고 또는 서비스 주소를 둘 수 있다.

**사용자 흐름**

1. 하단 메뉴의 통계를 누른다.
2. 월간 통계와 지표의 계산 기준을 확인한다.
3. 공유 카드 만들기를 누른다.
4. 이미지 미리보기에서 공유할 정보를 검토한다.
5. 이미지 저장을 누르거나, 브라우저·기기가 지원하면 공유하기를 사용한다.
6. 이미지 파일 공유가 지원되지 않는 환경에서는 PNG 다운로드를 기본 대안으로 제공한다.

**개인정보·저작권 원칙**

- 사용자 이름, 이메일, 상세 시청 이력 등은 기본 공유 카드에서 제외한다.
- 공유 전에 미리보기를 보여주고 사용자가 직접 저장·공유하도록 한다. 자동 게시하지 않는다.
- 초기 카드에는 영화·드라마 포스터를 기본 포함하지 않고, 타이포그래피와 자체 도형으로 디자인한다. 포스터 등 제3자 이미지를 넣으려면 사용권을 확인한다.
- 공유 URL에 개인 기록이나 식별 가능한 데이터를 담지 않는다.
- Web Share API를 통한 이미지 공유는 지원 브라우저·기기에서만 제공하며, 미지원 환경의 다운로드 경로를 함께 만든다.

**성공 지표 가설**

- 통계 탭 진입률
- 월간 리포트 생성률
- PNG 저장 시도율 및 지원 환경에서의 공유 실행률
- 공유 카드 사용자가 작품 기록을 추가로 남기는 비율
- 공유 기능 이용 후 7일 내 재방문 비율

공유 횟수만으로 성공을 판정하지 않는다. 기록을 남기는 행동과 재방문에 도움이 되는지를 함께 확인한다.

## 7. 기능 우선순위

- 구독 서비스, 실제 결제액, 결제일의 생성·수정·삭제

- 사용자 데이터 저장·수정·삭제

- 개인정보 수집 항목과 목적 안내

- 결제일 전 앱 내 알림 또는 캘린더 내보내기
- 이메일 로그인 또는 소셜 로그인

- 간단한 월간 요약 카드
- 월간 통계 화면: 이번 달 기록한 작품 수, 주 장르, 가장 많이 기록한 OTT
- 월간 통계를 세로형 이미지(PNG)로 저장·공유하는 카드

### P2 — 사용자 수요와 데이터 권한을 확인한 뒤

- 브라우저 확장 프로그램을 통한 시청 기록 수집
- 고도화된 개인화 추천
- 연말결산 카드와 공유 기능
- 자동화된 복수 OTT 기록 통합

## 8. 추천 로직 — AI 없이 먼저 검증

초기 추천은 다음 규칙으로 구성한다.

1. 사용자가 현재 구독 중이라고 등록한 OTT에서 제공되는 작품을 우선 노출한다. 제공처 데이터가 불확실할 경우 '확인 필요'로 표시한다.
2. 선호 장르 또는 사용자가 찜한 작품의 장르와 맞는 작품을 위로 올린다.
3. 봤어요 및 관심 없음으로 표시한 작품은 기본 추천에서 제외한다.
4. 찜한 작품 중 공개 일정이 확인된 작품은 별도 섹션에서 보여준다.
5. 추천 이유를 사용자에게 설명한다.

초기에는 추천의 정확도와 사용자가 실제로 하나의 작품을 선택하는지를 확인한다. 사용자 행동 데이터가 충분히 쌓이기 전에 AI 모델을 개발하지 않는다.

## 9. 데이터 수집 및 외부 데이터 전략

### 사용자 데이터 — 첫 버전은 최소 입력

- 구독 중인 OTT
- 실제 결제액·주기·다음 결제일
- 선호 장르
- 사용자가 직접 표시한 찜·봤어요·관심 없음 상태
- 선택 사항: 시청 기록 파일 업로드

### 자동 시청 기록 수집에 대한 원칙

- 넷플릭스는 계정 시청 기록을 CSV로 다운로드할 수 있는 공식 경로를 안내한다. 실제 파일의 열과 포함 정보를 확인한 뒤 해당 형식만 지원한다.
- CSV에 작품과 날짜가 있다고 해서 정확한 시청 시간, 재생 분량, 여러 OTT의 기록이 모두 제공된다고 가정하지 않는다.
- 티빙·웨이브 등 각 OTT의 다운로드/API 가능 여부는 사업자별로 별도 확인한다. 기능이 있다고 확인되지 않은 경우 '미지원/확인 중'으로 기록한다.
- 브라우저 확장은 기술적으로 가능한 경우가 있지만 OTT별 구현과 사이트 변경 대응이 필요하고, 모바일 앱·스마트TV에서의 재생까지 자동으로 기록하지 못한다.
- 사용자에게 계정 비밀번호를 요구하지 않는다. 제3자 데이터 수집은 공식 API·계약·약관·개인정보 관련 요건을 확인한 뒤 구현한다.

### 콘텐츠 제공처와 메타데이터

- 작품 제목·장르·줄거리·포스터·제공 OTT 데이터는 저작권과 API 약관을 확인한 범위에서만 사용한다.
- TMDB Watch Providers API 등 외부 제공처 API는 상업적 사용 조건과 필요한 표시 요건을 확인한다.
- JustWatch 또는 다른 서비스의 정보를 허가 없이 크롤링해 데이터베이스화하지 않는다.
- 초기 검증은 이용 조건을 확인한 소규모 카탈로그로 시작할 수 있다.
- 제공처 정보는 국가 및 시점에 따라 달라질 수 있으므로 기준 국가(초기: 대한민국)와 최종 확인 시각을 관리한다.

### 개인정보·보안 기본 원칙

- 필요한 항목만 수집하고 목적·보관 기간·삭제 경로를 사용자에게 안내한다.
- 외부 사용자에게 서비스할 때는 사용자별 접근 권한, 안전한 인증, 데이터 삭제, 전송 구간 HTTPS 등을 갖춘다.
- 프런트엔드 코드에 비밀 API 키를 넣지 않는다.
- 실제 결제 카드 번호나 OTT 비밀번호는 수집하지 않는다.

## 10. 경쟁사 벤치마킹

표는 공식 사이트·앱 설명에서 확인한 대표 기능을 요약한 것으로, 모든 요금제와 국가별 기능을 완전히 비교한 것은 아니다. 기능은 수시로 바뀔 수 있으므로 출시 전 다시 확인한다.

| 서비스 | 참고할 점 | 우리가 단순 복제하지 않을 점 |
|---|---|---|
| 키노라이츠 | 국내 OTT 통합 검색, 제공처·가격 정보, 신작/종료 예정, 평점·리뷰, 취향 분석·구독 관련 분석 | 통합 검색이나 취향 분석만으로 차별화한다고 주장하지 않는다. |
| JustWatch | 여러 스트리밍 서비스 제공처 필터, 개인화 추천, 통합 Watchlist, 신작 타임라인 | 검색·찜 목록만으로 직접 경쟁하지 않는다. |
| Trakt | 시청 이력, Watchlist, 평점, 개발자 API, 일부 서비스 자동 동기화 | 전체 기록을 강제로 입력하게 하지 않는다. 자동 동기화는 지원 범위를 정확히 알린다. |
| 기존 OTT 앱 | 각 플랫폼 자체 추천과 시청 경험 | 기존 추천 알고리즘을 이기겠다는 전략보다 여러 서비스 간 선택과 결제 의사결정에 집중한다. |

### 차별화 가설

기록을 꼼꼼히 관리하는 사람을 위한 트래커가 아니라, 기록하기 귀찮은 사람도 '지금 볼 것'과 '다음 달 구독할 것'을 결정할 수 있는 도구.

이 문구는 현재의 포지셔닝 가설이다. 실제 사용자 인터뷰에서 기존 서비스 대비 차이를 인식하는지 검증해야 한다.

## 11. 사업성 검증 계획 — 30일

### 1주 차: 문제 인터뷰

- OTT를 2개 이상 구독하는 사람 10~15명을 모집한다.
- 최근 '뭐 볼지 몰라서 안 본 경험', 구독을 유지한 이유, 실제로 해지한 경험을 묻는다.
- 기존에 사용하는 서비스와 사용하지 않는 이유를 확인한다.
- 자신의 시청 기록을 기록하는 데 어느 정도 노력을 들일 의향이 있는지 확인한다.

### 2주 차: 프로토타입 테스트

- 핵심 화면 5개를 Figma 또는 클릭 가능한 웹 프로토타입으로 연결한다.
- 사용자 5명에게 실제 과업을 수행하도록 요청한다.
- 과업: 구독 2개 등록 → 오늘 볼 작품 선택 → 찜하기 → 다음 결제일 확인.
- 설명 없이 어느 단계에서 막히는지 관찰한다.

### 3주 차: 동작하는 MVP

- P0 기능만 구현한다.
- 실제 데이터 대신 테스트 카탈로그를 사용해도 되지만 가상 데이터임을 분명히 표시한다.
- 저장·수정·삭제, 데이터 동기화, 월 합계 계산을 확인한다.

### 4주 차: 실사용과 재방문 확인

- 5~10명이 각자 구독 정보로 사용하도록 한다.
- 첫 세션 완료율, 찜 기능 사용 여부, 구독 관리 확인 여부, 7일 내 재방문, 추천을 통해 작품을 선택했는지 기록한다.
- 사용자가 직접 표현한 지불 의향과 다음 달에도 쓸 의향을 물어본다.

### 제안하는 초기 실험 지표

다음은 업계 평균이 아니라 내부 의사결정을 위한 초기 목표 예시다. 첫 실험 결과에 따라 조정한다.

- 10~15명 인터뷰 완료
- 5명 이상이 핵심 시나리오를 도움 없이 완료
- 테스트 사용자의 절반 이상이 추천 목록에서 작품을 찜하거나 선택
- 테스트 사용자가 실제 구독 상태를 한 번 이상 검토
- 7일 이내 재방문 의향과 실제 재방문 기록 확인

숫자만 통과했다고 사업성이 입증되는 것은 아니다. 인터뷰·관찰 결과와 함께 이탈 이유를 분석한다.

## 12. SWOT — 검증할 가설

| 요소 | 초기 가설 | 대응 전략 |
|---|---|---|
| Strengths 강점 | 시청 기록이 없어도 구독 정보와 찜 목록으로 시작할 수 있다. | 가입·입력을 최소화하고 핵심 가치를 빠르게 보여준다. |
| Weaknesses 약점 | 제공처 정보와 공개 일정의 정확성 확보가 어렵다. | 데이터 범위를 작게 시작하고 출처·확인 시점을 관리한다. |
| Opportunities 기회 | 작품 선택과 구독 결정을 하나의 흐름으로 연결할 수 있다. | '오늘 뭐 볼까?'와 '다음 달 구독할까?' 시나리오를 검증한다. |
| Threats 위협 | 키노라이츠·JustWatch·Trakt 등 기존 서비스와 기능이 겹친다. | 입력 부담, 결정 지원, 실제 행동 변화에서 차이가 있는지 비교 실험한다. |

## 13. 수익 모델 가설

초기에는 수익화를 구현하기보다 반복 사용 가치를 확인한다. 사용자가 돌아오지 않는다면 유료 기능을 추가해도 지속 가능성이 낮다.

1. **무료 핵심 기능 + 유료 상세 리포트:** 여러 달 이용 패턴과 구독 계획을 제공한다. 실제 결제 의향을 인터뷰로 확인한다.
2. **월간 구독 점검 서비스:** 일정한 주기로 구독과 찜 목록을 정리하도록 돕는 기능. 월간 재방문이 확인될 때만 고려한다.
3. **제휴 수익:** 이용자에게 실제로 유리한 선택을 훼손하지 않는 조건에서만 검토한다. 광고·제휴 여부는 투명하게 표시한다.

초기부터 추가 OTT 구독을 유도하는 제휴를 핵심 수익원으로 삼으면 '사용자의 구독료 절약'이라는 가치와 이해관계가 충돌할 수 있다.

## 14. Flutter로 전환할지 판단하는 조건

다음 조건이 여러 개 충족될 때 Flutter를 포함한 네이티브 앱 개발을 재검토한다.

- 사용자 테스트에서 핵심 흐름과 반복 사용 가치가 확인됐다.
- 사용자 다수가 앱스토어에서 설치 가능한 앱을 명시적으로 원한다.
- 푸시 알림·백그라운드 작업·공유 연동 등 웹에서 제약이 있는 기능이 핵심 가치가 됐다.
- 로그인한 사용자들의 다중 기기 이용과 계정 동기화가 필요해졌다.
- 유지보수할 수 있는 개발 시간과 기술 역량이 확보됐다.

그 전에는 모바일 우선 반응형 웹앱으로 가설을 검증한다. PWA 설치 기능은 웹앱 경험이 안정화된 뒤 추가한다.

## 15. 첫 번째 완료 기준

첫 MVP는 다음 흐름이 오류 없이 가능하면 충분하다.

1. 사용자가 OTT 2개와 실제 결제 금액·결제일을 등록한다.
2. 월 환산 총액이 정확하게 계산된다.
3. 사용자는 선호 장르를 입력하거나 건너뛴다.
4. 홈에 추천 작품 3~5개가 표시되고 추천 이유가 보인다.
5. 사용자가 찜하기·봤어요·관심 없음을 선택한다.
6. 상태가 보관함과 상세 화면에 반영된다.
7. 사용자는 다음 결제일과 구독 검토 상태를 확인·수정한다.
8. 새로고침하거나 다시 로그인해도 데이터가 올바르게 유지된다(저장 방식을 사용하는 경우).
9. 모바일 화면에서 주요 과업을 완료할 수 있다.
10. 데이터 출처가 불명확할 때 확인되지 않은 제공처·공개 일정을 단정하지 않는다.

## 16. 현재 HTML·CSS 프로토타입 현황과 반영 계획

사용자가 제공한 시작 코드는 다봄의 홈 화면 구조와 기본 다크 테마를 이미 잡아 둔 UI 프로토타입이다. 전체를 폐기하고 다시 만들기보다 기존 코드를 작은 단위로 기능화한다.

### 현재 코드에 있는 UI

- 헤더: Dabom. 로고와 프로필 영역
- 히어로: '오늘 어떤 작품을 다봄 하셨나요?' 문구와 제목 검색 입력창
- 지금 시청 중: 작품 카드, OTT 태그, 시즌/회차 진행률, + 1화 다봄 버튼
- 최근 다봄 기록: 작품명, 날짜, 평점
- 하단 네비게이션: 홈, 통계, 프로필 아이콘
- 디자인: 어두운 배경과 카드, 민트색 포인트(#00FFD1), 모바일 폭 중심의 레이아웃

### 현재 코드에서 기능화가 필요한 부분

- 검색 입력창은 검색 결과와 연결해야 한다.
- + 1화 다봄은 단순한 버튼 모양에서 끝나지 않고 회차 진행률과 기록 날짜를 갱신해야 한다. 같은 회차를 중복해서 완료 처리하지 않도록 한다.
- 최근 기록은 버튼 동작과 같은 데이터에서 생성돼야 하며, 날짜와 선택적 평점을 실제 기록에서 표시해야 한다.
- 하단 메뉴는 실제 화면 이동과 연결한다. 현재의 div 메뉴는 가능하면 접근성을 위해 버튼 또는 링크 요소로 바꾼다.
- 포스터 플레이스홀더는 실제 사용권이 확인된 데이터 또는 명확히 표시된 테스트 이미지로 교체한다.
- 제공된 예시의 2026.02.14, 2026.02.10 등의 날짜와 작품명은 데모 데이터다. 실제 사용자의 기록인 것처럼 보이지 않도록 개발용 가상 데이터로 표시하거나 비워 둔다.
- 공유된 메시지에서 CSS 주석이나 HTML 기호가 역슬래시 등으로 이스케이프돼 보이는 경우, 실제 소스 파일에서는 유효한 문법인지 확인한다. CSS 주석은 일반적으로 `/* 주석 */` 형식을 사용한다.

### 기존 코드에 추가할 통계 연결

- 하단 chart-bar 메뉴를 월간 통계 화면으로 연결한다.
- 홈에서 기록한 OTT, 작품 ID, 대표 장르, 완료 날짜, 에피소드 번호(시리즈인 경우), 평점(선택)을 통계 계산에 사용한다.
- 작품 기록이 추가되면 홈의 최근 기록과 월간 통계가 같은 데이터에서 자동 갱신돼야 한다.
- 통계는 P1 확장 기능이다. 먼저 시청 기록과 저장 기능을 정확하게 구현한 다음 추가한다.

### 권장 최소 데이터 모델 예시

```js
// works: 작품 정보(작품 자체의 메타데이터)
{
  id: "work_001",
  title: "예시 작품",
  type: "series", // "movie" | "series"
  primaryGenre: "드라마"
}

// watchRecords: 사용자 행동을 기록하는 이벤트
{
  id: "record_001",
  workId: "work_001",
  platform: "Netflix",
  eventType: "episode_completed", // 또는 "title_completed"
  episodeNumber: 3, // 시리즈가 아니라면 생략 가능
  recordedAt: "2026-10-21",
  rating: null
}
```

이 구조는 설명용 예시다. 실제 데이터 모델은 한 회차의 중복 완료, 작품의 OTT별 제공처 차이, 시리즈 시즌별 진행률을 어떻게 관리할지 정한 뒤 확정한다. 브라우저의 localStorage는 개인 기기에서 기능을 검증할 때 사용할 수 있지만, 여러 사용자가 실제로 이용하는 서비스로 공개할 경우 인증과 사용자별 데이터 분리가 있는 서버 저장소가 필요하다.

## 17. Claude에게 전달할 구현 요청 프롬프트

아래 프롬프트를 이 문서와 함께 Claude에 전달한다.

> 이 문서를 제품 요구사항의 기준으로 삼아 줘. 먼저 기존 HTML·CSS 프로토타입을 살펴보고 현재 폴더·기능을 파악해. 기존 UI를 불필요하게 전부 갈아엎지 말고, 현재 코드에서 바로 재사용할 수 있는 부분을 설명해 줘. 먼저 P0 요구사항만 구현하고 P1·P2를 임의로 한꺼번에 추가하지 마. 화면은 모바일 우선 반응형으로 만들고, 시작 설정·홈·작품 보관함·구독 관리·작품 상세 5개 핵심 화면을 구현해 줘. + 1화 다봄 버튼, 검색, 하단 메뉴를 실제 기능과 연결하고 기록은 여러 화면에 일관되게 반영해 줘. 월간 통계와 PNG 공유 카드는 P1 기능으로 정의된 계산 규칙과 개인정보 원칙에 따라 별도 단계로 구현해 줘. 통계는 실제 기록된 데이터만 사용하고, 시청 시간 값이 없으면 총 시청 시간을 만들어 내지 마. 추천은 초기에는 규칙 기반으로 만들고 추천 이유를 노출해 줘. 확인하지 않은 OTT 제공처나 공개 일정을 사실처럼 표시하지 말고, 테스트 데이터는 가상 데이터라고 표시해 줘. OTT 비밀번호를 수집하거나 무단 스크래핑을 추가하지 마. 저장 방식·인증·보안상 한계를 설명하고, 테스트할 시나리오와 완료 기준도 함께 작성해 줘.
